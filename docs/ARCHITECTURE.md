## 2. Tech Stack

### 2.1 Core Framework

Flutter (Dart) + Riverpod with **hand-written** providers — no `riverpod_generator`, no `build_runner`, no `.g.dart` output (see `CLAUDE.md` → Riverpod). `go_router` for routing, plain immutable domain classes (no freezed), `very_good_analysis` lints. See `wavecrux/docs/ARCHITECTURE.md` §2.1 for the shared rationale.

### 2.2 Domain Engine

SimCrux does not embed a simulator. Its engine is the orchestration layer around external ones:

- **Config** — `ConfigLoader` (`lib/services/config/config_loader.dart`) parses `simcrux.yaml` into a `RegressionConfig` of `TestSpec`s (includes, `.f` filelists, sweeps, defaults → suite → test inheritance).
- **Drivers** — every simulator is a `SimulatorDriver` (`lib/domain/interfaces/simulator_driver.dart`). The built-ins extend `ProcessBackedSimulatorDriver` (`lib/services/simulator/process_backed_simulator_driver.dart`), which owns spawning, streaming, timeout escalation and process-tree reaping. `simulatorDriverRegistryProvider` (`lib/services/job_scheduler/job_scheduler_provider.dart`) registers six: `icarus` (`iverilog` → `vvp`), `verilator` (`verilator --cc --exe --build`, then the built model), `ghdl` (`ghdl -a` / `-e` / `-r`), `cocotb` (`make` over Cocotb's `Makefile.sim` — see [`cocotb-strategy.md`](cocotb-strategy.md)), `riscv_arch` (one architectural-compatibility test per job: cross-compile, reference model, DUT, signature compare) and `riscv_formal` (one SymbiYosys bounded proof per job, verdict read from `sby`'s `DONE` line). A hidden no-spawn `demo` driver is added only when `SIMCRUX_DEMO_RUNNER` is set. Plugin-contributed drivers resolve through the same registry (§10, custom simulator-driver plugin SDK).
- **Binary resolution** — `simulators.<id>.source` in `simcrux.yaml`: `system` and `bundled` both resolve the bare executable on `PATH` (nothing is bundled); `custom` uses `path:`. On macOS and Windows the spawned engine's `PATH` is augmented with the Homebrew / persistent-registry directories a GUI launch would otherwise miss (`crux-shared/packages/crux_io/lib/src/engine_path_augmentation.dart`, the one copy every engine-spawning product uses). A Settings → Simulators path override applies only in the desktop app and only to a simulator the project's `simulators:` block does not already name — the YAML entry wins, and the headless `--ci` runner never reads Settings.
- **Scheduling** — `LocalJobScheduler` (`lib/services/job_scheduler/local_job_scheduler.dart`) runs compile + execute per test under bounded concurrency, named resource locks, per-test timeouts, the retry policy and dump retention, in a per-test work dir under `{runRoot}/runs/{runId}/{testIdSafe}/`.
- **Pass/fail** — after every execute the scheduler classifies the captured output through the test's configured detector (`lib/services/pass_fail_detector/`: `exit_code`, `string_match`, `regex`, `uvm_report`, `cocotb`, `golden_compare`, plus the `composite` and `use` combinators); only when the detector returns `unknown` does the driver's own status stand.
- **Results** — an in-memory `ResultStore` feeds the dashboard; `results.ndjson` is streamed during a run (`lib/services/result_store/streaming_results_writer.dart`); `SqlTrendStore` persists history to `trends.db` (§6.5); exporters in `lib/services/export/` write JSON, JUnit, CSV and HTML.
- **Headless** — `bin/simcrux.dart` is the Flutter-free CLI (built by `tool/build_cli.sh`); the app binary also accepts `--ci`, `export-dashboard`, `--import-fusesoc`, `import-riscv-arch-test` and `import-riscv-formal` without opening a window (`lib/app.dart`).

### 2.3 Rendering

Standard Flutter widget tree. No `CustomPainter`/`RenderObject` visualisations are needed yet; the results table, inspector and log panes are ordinary widgets.

### 2.4 Panel Layout

`SimcruxIdeLayout` (`lib/features/panel_layout/widgets/simcrux_ide_layout.dart`) is a thin adapter over the shared `CruxIdeLayout` from `crux_ide_layout`, which wraps the `panes` package — the four-pane desktop layout (test browser, results dashboard, inspector, log stream). The web viewer does not use it (see §3).

### 2.5 Infrastructure

GitHub Actions (`.github/workflows/`): `ci.yml` runs analyze (`--fatal-infos --fatal-warnings`), tests, desktop and web builds and a supply-chain check — Linux on every push to `main`, all three desktop platforms on pull requests and on a weekly schedule. `web-deploy.yml` (manual) publishes the web viewer to Cloudflare Workers Static Assets (`wrangler.jsonc`). This repo carries no desktop release workflow; the in-app update check reads the manifest named in `lib/core/update/simcrux_update_config.dart`.

## 6. Architecture

### 6.1 Layer Responsibilities

Same pattern as WaveCrux:

- **Domain layer** (`lib/domain/`) — Pure Dart, zero Flutter imports.
- **Services layer** (`lib/services/`) — Business logic.
- **Feature modules** (`lib/features/`) — Each owns its providers, screens, widgets.
- **Core** (`lib/core/`) — Theme, router, shortcuts and the action-dispatch map, CLI parsing, update/telemetry glue.
- **Plugins** (`lib/plugins/`) — App-level extension-point providers (extra localization delegates, status-bar trailing widgets).
- **Shared** (`lib/shared/`) — Widgets and platform helpers used by more than one feature.
- **Web** (`lib/web/`) — The read-only web viewer's screen, loaders and widgets (§3).

### 6.2 Dependency Flow

```
features/ → services/ → domain/ (via interfaces)
services/ → domain/ (implements interfaces, uses models)
core/ → anything below features/, plus the composition root (below)
plugins/ → domain/ + services/, never features/
```

The load-bearing invariants, in strict order of importance:

1. **`domain/` is pure.** No Flutter, no Riverpod, no imports of `services/`,
   `features/`, `core/`, or `plugins/`. A pure data class that a service or
   feature needs lives in `domain/` — it never reaches up. (A pure model that
   drifts into `features/` or `services/` and gets imported downward is the
   most common form of this rot: `DashboardRow` and `ConfigLoaderError` were
   both pure data misfiled above `domain/` and imported upward by services;
   both moved to `domain/models/`.)
2. **`services/` must not import `features/`.** A service that reaches into a
   feature provider is misfiled: if it is a pure model, it belongs in
   `domain/`; if it is a coordinator/provider (a `Notifier` or provider that
   wires feature state together — e.g. the auto-reload controller, the
   config-loader provider, the workspace↔registry sync), it belongs in the
   owning **feature** module, not `services/`. The pure mechanism it drives
   (the file watcher, the `ConfigLoader`, the project registry) stays in
   `services/`; only the wiring moves up.
3. **`plugins/` must not import `features/`.**

**The composition-root ("wiring tier") exception.** A small, explicitly
sanctioned set of `core/` files legitimately reach into `features/` because
their entire job is to wire concrete features into the app at startup:

- `core/router/app_router.dart` — maps routes to concrete feature screens.
- `core/theme/simcrux_color_theme_bootstrap.dart` — bridges the settings
  feature's persisted theme overrides into the `crux_theme` runtime.
- `core/shortcuts/simcrux_action_handlers.dart` — the `SimcruxAction` →
  handler map the keyboard shortcuts, menu bar and command palette all
  dispatch through; it must reach every feature's opener or provider.

These are the app's composition root, mirroring the suite-wide "wiring tier"
precedent (the Pro overlay's override builders play the same role). They are
**not** a licence to import features from arbitrary `core/` utilities. New
composition-root seams are a conscious, reviewed decision.

All of the above is enforced automatically by
`test/static/import_layering_test.dart` — an auto-discovering guard
whose only sanctioned exceptions are the three composition-root files above,
held in a commented allowlist. Adding a `services/`→`features/` or a
`domain/`→up import turns it red with a `path:line` pointer to the offender.

### 6.4 Riverpod Provider Hierarchy

SimCrux uses WaveCrux's per-tab and per-pane container architecture (`wavecrux/docs/ARCHITECTURE.md` §6.4). `bootstrap()` in `lib/app.dart` calls `createWorkspaceContainers` (`lib/features/workspace/providers/workspace_containers.dart`), which builds:

- a **root** `ProviderContainer` carrying the bootstrap overrides — CLI args, the theme bridge, the update / issue-reporter / audit / telemetry bindings, and then the Pro overlay's `extraOverrides`, spread last so they win;
- a **scoped** child container, the one the widget tree reads. `runApp` mounts both through `WorkspaceContainersScope`: the root above the scoped container, although nothing reads the root through the tree. Riverpod gives every container its own scheduler, and a scheduler refreshes providers in step with the frame only while its container is mounted; unmounted, the root's providers (every provider nothing overrides) refreshed on a timer, and a frame that came first rebuilt their watchers while they were dirty, which asserts `markNeedsBuild() called during build`. `test/features/workspace/widgets/workspace_containers_scope_test.dart` fails that way when the root is left out;
- `crux_workspace`'s `TabContainerManager` / `PaneContainerManager`, which parent one child container per workspace tab / pane under the root. Per-tab overrides come from `simcruxTabOverridesFactoryProvider` (default: the `simcruxTabOverrides` list in §10); per-pane overrides from `simcruxPaneOverrides`.

The headless `--ci` and `export-dashboard` paths build a single transient `ProviderContainer` with the same telemetry overrides and `extraOverrides`, so a Pro override reaches them without the widget tree.

### 6.5 Run Lifecycle, Cancellation & Shutdown

A regression run spawns real simulator subprocesses, so cancellation and app exit must reap them deterministically rather than leaking process trees:

- **`ActiveRunRegistry`** (`lib/services/lifecycle/active_run_registry.dart`) — the set of in-flight runs, each registered with a canceller closure. `cancelAll(grace:)` invokes every canceller and waits, bounded by the grace budget; a throwing or hung canceller cannot block the others.
- **`AppExitCoordinator`** (`lib/services/lifecycle/app_exit_coordinator.dart`) — both quit paths (File → Quit and OS-initiated termination) route through `shutdown()`, which drains the registry under `kDefaultShutdownGrace`. It is re-entrant-safe: a second quit awaits the same in-flight drain rather than returning early and letting the caller `exit(0)` before the reap finishes.
- **`LocalJobScheduler` cancellation** (`lib/services/job_scheduler/local_job_scheduler.dart`) — a cancel routes `driver.cancel(testId)` to the live test's driver, which reaps its process tree (SIGTERM → grace → SIGKILL). Both the **compile** and **execute** stages register their live test, and each stage is bounded by the per-test timeout, so a long compile is reaped on cancel/quit and a post-compile cancel never dispatches execute.
- **`ResourceLockTable`** (`lib/services/job_scheduler/resource_lock_table.dart`) — the per-run resource-lock mutual-exclusion extracted so the grant/transfer invariant is unit-testable under a forced interleaving.
- **`--fail-on-vacuous`** — the CI failure tally (`countFailures`, `lib/services/ci/ci_runner.dart`) always counts `fail` + `timeout` + `unknown`; `vacuous` is opt-in via this flag. `unknown` is always a failure because a run that could not determine pass/fail has not passed.
- **Trend DB migration v3** (`lib/services/trend_store/sql_migrations.dart`) — adds `idx_runs_started` so the recent-runs windows (`recentDeltas` / `distinctTestIds` / `recentTrendsFor`) open on an index rather than a full scan of the `runs` table.

## 8. Coding Standards & Conventions

See `CLAUDE.md` for the binding day-to-day rules. The detailed rationale and the cross-platform mobile UI rules live in WaveCrux's `ARCHITECTURE.md` §8. simcrux inherits the Dart style, Riverpod, and testing conventions verbatim.

### 8.9 Test Fixture & Validation Strategy

Shipped for the orchestration domain. simcrux's data domain is the regression run, so the fixture corpus is a set of deterministic orchestration scenarios (`test/fixtures/orchestration/`, plus `test/fixtures/fusesoc/` and `test/fixtures/projects/`, mirrored under `verification/fixtures/orchestration/`) driven through the `FakeProcessRunner`/`orchestration_fixture.dart` harness rather than real simulator subprocesses. Static guard tests keep the corpus honest: `test/static/orchestration_fixture_layout_test.dart` and `orchestration_fixture_companion_test.dart` enforce the directory-is-the-catalog layout, and `no_real_process_spawn_in_unit_tests_test.dart` blocks accidental real spawns in unit tests. **The corpus guards check validity, not just presence** — the companion test parses every committed `simcrux.yaml` through the real `ConfigLoader`, and `orchestration_golden_test.dart` diffs the loaded specs against the specs each scenario's scheduler replay actually runs. Existence checks alone let the three committed configs drift into a schema the loader rejects while the whole suite stayed green. The layered validation ideas from WaveCrux (known-answer fixtures, golden output) still apply as simcrux grows richer output surfaces.

The fixture harness itself — `lib/services/job_scheduler/fake_process_runner.dart` and `orchestration_fixture.dart` — lives in `lib/`, not `test/`, deliberately: the `tool/generate_orchestration_fixtures.dart` generator (which writes both `test/fixtures/orchestration/` and its `verification/fixtures/orchestration/` mirror) and the `tool/soak/` regression soak both import it, and code outside `test/` cannot import from `test/`. It is test *machinery*, not shipped product behavior; the `no_real_process_spawn` guard ensures it can never launch a real subprocess.

## 10. Extension Points (Pro Overlay Seams)

simcrux is consumed by the closed-source Pro overlay through Riverpod provider overrides, not through code forking. The pattern matches WaveCrux exactly:

- `simcrux` (this repo) ships the complete standalone tool.
- The Pro overlay consumes this repo as a Git submodule, `path: ./simcrux` in pubspec, and layers `proOverrides` into the `bootstrap()` `ProviderScope`.

When a Pro feature needs to plug into the open-core somewhere there is no hook yet, the *first* change is to this repo: define the interface, add the registry / Riverpod provider, ship a default no-op or open-core implementation. Only then does the Pro implementation land in the Pro overlay (after a submodule pin bump). Forking open-core code in the Pro overlay is not allowed — see `CLAUDE.md` for the binding rule and `wavecrux/docs/ARCHITECTURE.md` §10 for the worked examples.

### Override pattern

```dart
// lib/app.dart (abridged)
Future<bool> bootstrap({
  List<String> args = const [],
  List<Override> extraOverrides = const [],
}) async {
  WidgetsFlutterBinding.ensureInitialized();
  // … CLI sub-commands and --ci run here and `return true` before runApp;
  // runSimcrux then flushes and exits, because a desktop runner keeps its
  // window alive after main returns …
  final containers = createWorkspaceContainers(
    rootOverrides: <Override>[
      cliArgsProvider.overrideWithValue(parsedArgs),
      simcruxCruxColorThemeOverride,
      ...simcruxUpdateOverrides,
      ...simcruxIssueReporterOverrides,
      ...simcruxTelemetryOverrides,
      ...extraOverrides, // the Pro overlay spreads its proOverrides here
    ],
    scopedOverrides: simcruxIssueReporterScopedOverrides,
  );
  runApp(
    WorkspaceContainersScope(
      root: containers.root,
      scoped: containers.scoped,
      child: const AppExitGuard(child: SimcruxApp()),
    ),
  );
  return false;
}
```

Both entry points call `runSimcrux` (which runs `bootstrap` and exits after a headless invocation); the Pro overlay passes `extraOverrides: proOverrides` and its own Linux desktop identity (`linuxDesktopApp:`, the AppImage `.desktop` entry; open core defaults to `kSimcruxLinuxDesktopApp` in `lib/core/platform/linux_desktop_identity.dart`, which must match `linux/CMakeLists.txt`) from its `lib/main.dart`. Open-core conflict semantics: open-core overrides come first; Pro overrides come last; later overrides win. The per-tab and per-pane containers (§6.4) are parented under the same root, so a root override is visible in every tab unless the tab re-binds that provider.

### Dashboard row extension surfaces (open-core)

The Pro overlay annotates dashboard rows with feature-specific trailing widgets (flaky-test classification chip, future trend-tracking sparks) without forking the open-core results table. The seam is one Riverpod provider:

- **`dashboardRowTrailingBuilderProvider`** (`lib/features/dashboard/providers/dashboard_row_extensions.dart`) — typedef `DashboardRowTrailingBuilder = Widget? Function(WidgetRef ref, DashboardRow row)`. Open-core default returns a builder that always emits `null`; the Pro overlay overrides this provider in `proOverrides` with a builder that watches `flakyDetectionServiceProvider`'s computed scores and returns a classification chip for tests classified as flaky. The chip is **deliberately not** paired with a per-row `SimCruxFeatureTierBadge`: badging every flaky row would flood the reserved column with `PRO` chips. The flaky-detection feature's tier badge lives once, on the surfaces that own the feature — the Flaky Tests panel header and the Settings → Flaky Test Detection section header — not on each annotated row. The reserved trailing column (120 dp) lives on both the header and body rows so the table layout never reshuffles when an overlay registers a real builder. Builder receives a `WidgetRef` so the Pro override can read per-row providers without rebuilding the entire table on every score change.
- **`dashboardRowContextMenuBuilderProvider`** (`lib/features/dashboard/providers/dashboard_row_extensions.dart`) — typedef `DashboardRowContextMenuBuilder = List<PopupMenuEntry<void>> Function(BuildContext, WidgetRef, DashboardRow)`. Open-core default returns an empty list (right-click / long-press are inert). The Pro overlay overrides this provider in `proOverrides` to attach a "Cross-probe to peer →" submenu enumerating connected CXP peers via `cxpPeersProvider`, per-row "Re-run with seed N" and "Re-run all in this parameter group" entries, and a trend-chart entry. Each entry routes through the Pro cross-probe originator / the existing "Debug in WaveCrux" path / `RegressionRunner.submitSpecs`. The dashboard row is wrapped in the shared `PlatformContextMenu` (`crux_ide_layout`), which opens a menu only when the builder produced any entries — so open-core behavior is unchanged when no overlay is loaded.
- **`extraDashboardActionsProvider`** (`lib/features/dashboard/providers/dashboard_actions_extensions.dart`) — returns `List<Widget>` rendered by the dashboard toolbar (`SimcruxToolbar`, `lib/features/dashboard/widgets/simcrux_toolbar.dart`) after its curated open-core buttons. Open-core default is empty (the toolbar shows only the general buttons). The Pro overlay populates the list with its toolbar widgets — re-run failures, seed-failure heatmap, compare to baseline, the two RISC-V dashboards, and a baseline status chip; each widget owns its own tier badge and `proFeatureUnlocked` check so the open-core consumer does not need to bake in tier checks.
- **`seedFailureHeatmapOpenerProvider`** (`lib/features/dashboard/providers/seed_failure_heatmap_opener.dart`) — `Provider<void Function(BuildContext)?>` that mounts the Pro Seed Failure Heatmap screen. Open-core default is `null`: the menu / command-palette entry stays visible so users discover the capability, and firing it shows the "requires SimCrux Pro" snackbar. The Pro overlay overrides the provider with a callback that checks `proFeatureUnlocked` (beta period + licence tier) — closed, it shows the upgrade dialog; open, it opens the screen in a desktop dialog. `SimcruxAction.openSeedFailureHeatmap` dispatches through this provider in `lib/core/shortcuts/simcrux_action_handlers.dart`.
- **`regressionComparisonOpenerProvider`** (`lib/features/dashboard/providers/regression_comparison_opener.dart`) — `Provider<void Function(BuildContext)?>` that mounts the Pro Regression Comparison screen. Mirrors the `seedFailureHeatmapOpenerProvider` shape: open-core default is `null` (the screen lives in the Pro overlay); the Pro overlay overrides the provider with a callback that opens the screen behind the same `proFeatureUnlocked` gate. The dashboard's Pro-tier "Compare to baseline" quick action and the baseline status chip both dispatch through this provider so the navigation logic lives in one place.
- **`riscvCompatibilityOpenerProvider`** (`lib/features/dashboard/providers/riscv_compatibility_opener.dart`) — `Provider<void Function(BuildContext)?>` that mounts the Pro RISC-V Compatibility Dashboard (per-extension rollup, ISA-string attestation, signature diff viewer). Same shape as the two openers above: open-core default is `null`, and the Pro overlay registers a callback that owns the `proFeatureUnlocked` gate so every caller is gated in one place. **What this seam does not gate:** the compatibility *verdict*. `riscv_arch` runs, classifies and records per-test pass/fail with no license, no row cap and no post-`kBetaPeriod` gate, and the ordinary dashboard renders every one of those rows in an unlicensed build — only the analysis screen is Pro. Do not consistency-fix a tier check onto the driver, detector, comparator or config loader because this provider has one on the other side: a compatibility verdict is correctness, and correctness is free (`verification/VERIFICATION_GUIDE.md` §18).
- **`riscvFormalOpenerProvider`** (`lib/features/dashboard/providers/riscv_formal_opener.dart`) — `Provider<void Function(BuildContext)?>` that mounts the Pro RISC-V formal property dashboard (per-property verdicts, the `depth_reached` / `depth_configured` pair, RVFI check-set coverage grouped on `riscv.formal.group`, and the counterexample→WaveCrux hand-off). Same shape and same doctrine as `riscvCompatibilityOpenerProvider`: open-core default is `null`, the Pro overlay registers a callback that owns the `proFeatureUnlocked` gate. **What this seam does not gate:** the formal *verdict*. `riscv_formal` runs, reads `sby`'s `DONE (…)` line, classifies every bounded proof, records the whole `riscv.formal.*` metric set and hands over the counterexample VCD on `TestResult.waveformPath` with no license and no post-`kBetaPeriod` gate. A proof that says a property does not hold is correctness, and correctness is free (`verification/VERIFICATION_GUIDE.md` §18).
- **`failOnRegressionPolicyProvider`** (`lib/services/ci/fail_on_regression_policy.dart`) — `Provider<FailOnRegressionPolicy>` consulted by `CiRunner` when both `--ci` and `--fail-on-regression` are set. Open-core default is `NoopFailOnRegressionPolicy` (always returns `FailOnRegressionDecision.pass`, so an open-core build never fails CI on regression). The Pro overlay overrides the provider with a concrete policy that reads `CliArgs.baselineRunPath` (a `.ndjson` snapshot produced by a prior `--ci` run), parses it into a `TestRun`, runs `RegressionComparisonEngine.compare(baseline, candidate)`, and returns `(diff.isRegression, exitCode)` — exit code defaults to `1`, override via the `SIMCRUX_REGRESSION_EXIT_CODE` env var. A `--baseline` file that is missing, unreadable or holds no results fails the gate with exit `2` and an `error: regression gate:` line on stderr. `CiRunner.licenseTier` — the tier the `--ci` caller resolved with `HeadlessLicenseTierResolver`, the same one it loads the project at — is passed to every decision as `licenseTier:`, so the overlay's policy, which carries the paid engine, refuses the gate itself (exit `2`, same stderr prefix) when the tier does not include it once the beta ends. When `--fail-on-regression` is set without `--baseline`, the CI runner prints a warning, skips the regression gate and leaves the exit code to `--fail-threshold` (drift-friendly default).
- **`prAnnotationDispatcherProvider`** (`lib/services/pr_annotation/pr_annotation_dispatcher_provider.dart`) — `Provider<PrAnnotationDispatcher>` that posts a batch of `PrAnnotation`s to a configured `PrAnnotationTarget` (GitHub PR, GitLab MR, or generic webhook). Open-core default is `NoopPrAnnotationDispatcher` — open-core builds never POST anywhere; the per-platform HTTP implementations (GitHub Checks API, GitLab notes / discussions / pipelines, generic webhook) live in the Pro overlay behind a composite dispatcher. Per-annotation outcomes are first-class in the returned `PrAnnotationBatchResult` (`success` / `rateLimited` / `authFailed` / `networkError` / `platformError` / `unsupported`); dispatcher errors do not throw. Auth tokens carried by `PrAnnotationTarget.authToken` are redacted from `toString()` and excluded from `hashCode` contents (only their length contributes). ### Test parameterization & seed sweeps (open-core)

The Pro overlay's `seeds:` / `parameters:` sweep workflows plug into open-core through three additions, none of which depend on Pro-specific machinery:

- **`TestSpec.seeds: List<int>?`** and **`TestSpec.parameterSweeps: Map<String, List<String>>?`** — pre-expansion "template" fields populated by the config loader when it encounters a multi-value `seeds: [1, 2, 3]` block or a list-valued `parameters: { MEM_SIZE: ["1024", "4096"] }` entry. Both fields are `null` on every concrete (expanded) child spec. `TestSpec.isParameterized` is the convenience getter the loader and the expander consult.
- **`TestSpec.parentSpecId: String?`** + **`TestResult.parentSpecId: String?`** — on expanded children, references back to the un-expanded template's id so the Pro "Re-run all in this parameter group" workflow can re-issue every cartesian-product instance from a single parent. `TestResult.boundParameters: Map<String, String>?` mirrors the spec's `parameters` map on the in-memory result so a consumer can read the binding without re-parsing the synthesized `testId`; it is not serialized to NDJSON or the trend store. `TestSpec.displayName` is the human-readable label for an expanded child (`<suite>/<name> [seed=7, dataWidth=16, mode=fast]`); today the Pro seed-failure heatmap is its consumer (the dashboard table renders suite and test name columns).
- **`TestSpecExpander`** (`lib/services/config/test_spec_expander.dart`) — stateless `const` class (injectable through `ConfigLoader(expander:)`) that fans a parameterized [TestSpec] template into the concrete children the scheduler executes. Stateless `expand(TestSpec) → Iterable<TestSpec>` plus `expansionSize(TestSpec) → int` for runaway-protection guards. Expansion order is part of the public contract: seeds expand outermost, then parameter axes expand in declaration order (first axis advances slowest, last axis fastest). Tests pin this ordering so re-run workflows stay stable across releases. Wired into `ConfigLoader._parseSuite` so the scheduler never sees a parameterized template — it always sees the fully-bound children.

The loader gates the sweep blocks behind the active license tier. The `ConfigLoader` constructor takes a `LicenseTier` (open-core default `LicenseTier.openCore`) and a `betaPeriod` flag (open-core default `kBetaPeriod` from `crux_license`). When the gate is closed (post-beta openCore), `seeds:` / `parameters:` sweep blocks are **silently dropped** and a `ConfigLoaderError` with `severity: ConfigLoaderErrorSeverity.warning` is appended to the loaded `RegressionConfig.loadWarnings` list — the test runs once with the literal scalar value (or no seed). `CiRunner` prints every `loadWarnings` entry to stderr as `warning: path:line:col: message`, and the dashboard renders them in `ConfigLoadWarningsBanner` (`lib/features/dashboard/widgets/config_load_warnings_banner.dart`) above the results table, gated by the `showConfigLoadWarningsProvider` seam (open core: always; Pro: the Parameterization warnings switch). Single-element sweeps (`seeds: [7]`, `parameters: { MEM_SIZE: ["1024"] }`) collapse to scalar values before the gate consultation, so they pass through unaffected on Open Core.

A `kDefaultMaxExpansionSize = 10 000` ceiling rejects parameterized templates whose cartesian product would exceed the limit; the Pro overlay's Settings → Parameterization category lets a user raise it for GUI project loads in the current session (the value is not persisted). `configLoaderProvider` reads the active tier from `licenseTierProvider`; tests pass an explicit `licenseTier:` / `betaPeriod:` pair so they don't depend on the global `kBetaPeriod`. The headless `--ci` runner and `bin/simcrux.dart` have no licence controller, so both resolve the tier with `HeadlessLicenseTierResolver` (`lib/services/license/headless_license_tier.dart`: `--license-file`, then `SIMCRUX_LICENSE_FILE`, then the policy file's `license` key, validated offline by `CruxLicenseValidator.production`, with the suite grace period on expiry) and construct `ConfigLoader(licenseTier: tier)`. A machine file resolves only on the machine whose fingerprint it names, so for one of those the resolver passes the validator this machine's fingerprint from crux_license's `SharedInstallFingerprint`: the suite's shared `crux/license/install.fingerprint` under the application-data root, which every EDACrux product's licence store and CLI read and write, so a computer running several products counts as one machine. A headless run reads it, adopts the legacy per-product `simcrux.fingerprint` into it when it does not exist yet, or, on an agent where no product has ever run, mints it. The CLI binary cannot link the credential store, and on a build agent it would block on a prompt. They keep the default expansion ceiling and never read the desktop detector library.

`ConfigLoaderError.severity` drives the warning-vs-fatal split, and `RegressionConfig.loadWarnings` is the unmodifiable list that carries the advisories. Both are forward-compatible — callers that ignore them continue to work.

### Re-run query service (open-core)

The Pro "Re-run failures only" / "Re-run with seed N" / "Re-run all in this parameter group" workflows consume a single open-core service:

- **`ReRunQueryService`** (`lib/services/re_run_query/re_run_query_service.dart`) — abstract surface with `queryFailedSpecsFrom(runId)`, `queryGroupSpecsFor({parentSpecId, runId})`, and `trackSubmittedSpecs(specs)`. The `DefaultReRunQueryService` holds a spec inventory partitioned by project id and consults the active `ResultStore`'s `queryResults` stream filtered to `{ fail, timeout, unknown }` to resolve failing test ids back to their `TestSpec`s.
- **`reRunQueryServiceProvider`** (`lib/services/re_run_query/re_run_query_service_provider.dart`) — open-core Provider returning the default implementation, re-bound per workspace tab through `simcruxTabOverrides`. The service stays alive across runs and queries the active `resultStoreProvider` lazily so it survives the null-→-real-store transition that happens when the first run is submitted.
- **Submission tracking is automatic.** `RegressionRunner.start` and `RegressionRunner.submitSpecs` register every submitted `TestSpec` with the active `ReRunQueryService` before handing the request to the scheduler, so the inventory is always in sync with the dashboard's view of what ran. Callers do not need to call `trackSubmittedSpecs` themselves.
- **`RegressionRunner.submitSpecs(List<TestSpec> specs, {int concurrency = 4, RegressionTrigger trigger = RegressionTrigger.manual})`** is the dashboard's open-core submission path for partial re-runs. Cancels any in-flight run first, then reuses the active `RegressionConfig` (project file, simulator binaries, output config) and the active scheduler; creates a fresh `InMemoryResultStore` per re-run so a 3-test re-run does not visually overlay a 1000-test run; silently no-ops when `specs` is empty or no project is open. Pro re-run dispatchers (toolbar "Re-run failures only", per-row "Re-run with seed N", per-row "Re-run all in this parameter group") all dispatch through this single method.

The service is open-core because the underlying semantics (filter failed results, group by parent spec id) are pure-domain — every product tier sees the same surface. The Pro overlay overrides the provider only to supply a project-scope resolver, so the inventory partitions by the active project in multi-project mode; its re-run UI consumes the same surface.

### Per-test retry policy + seed capture (open-core)

The Pro overlay's flaky-detection auto-retry feature plugs into open-core through three additions, none of which assume anything about flakiness:

- **`TestSpec.seed: int?`** — explicit randomization seed pinned by the config loader (e.g. for `seeds: [1, 2, 3]` sweeps) or by a retry policy when scheduling a deterministic-replay retry. `null` means "driver decides" (typically system-clock-derived).
- **`TestResult.executionSeed: int?`** — captures the seed the simulator actually used so a non-deterministic run can be replayed. Drivers report it as `TestExecutionFinished.effectiveSeed` (the built-in `icarus`, `verilator`, `ghdl` and `cocotb` drivers resolve and pass a seed on every run), and the scheduler records `effectiveSeed ?? spec.seed`.
- **`RetryPolicy`** (`lib/domain/interfaces/retry_policy.dart`) + `retryPolicyProvider` (`lib/services/retry_policy/retry_policy_provider.dart`) — open-core abstract policy with two hooks: `shouldRetry({spec, lastResult, attemptsSoFar, maxAttempts})` and `nextSeedFor({spec, lastResult, attemptsSoFar})`. A policy whose decisions need async state may also implement `PreparableRetryPolicy.prepareForRun(specs)`, which the scheduler awaits (best-effort) before the first test of a run. Default registered implementation is [NoopRetryPolicy] (never retries). The Pro overlay overrides `retryPolicyProvider` in `proOverrides` with a flaky-detection policy that consults the active flaky scores. `LocalJobScheduler` invokes the policy from inside its per-test loop after a non-passing result and reruns the test with the policy-supplied seed; the scheduler enforces a hard `maxRetryCeiling` (default 5) so a misbehaving policy cannot loop indefinitely. Only the final attempt's `TestResult` is emitted to the run stream; intermediate retry results are consumed internally.

### Trend tracking extension surfaces (open-core)

The Pro trend-tracking screens build on top of an extended open-core `TrendStore` surface plus four opener providers that the Pro overlay wires up in `proOverrides`. None of the Pro charting / alerting code lives in this repo; only the data plumbing and discovery hooks do.

- **`TrendStore` (extended)** — `lib/domain/interfaces/trend_store.dart`. The core surface (`recordTrendPoint`, `recentTrend`, `recentDeltas`) is joined by methods with safe defaults: batch `recordTrendPoints`; `pointsForRun` (reloads a stored run, e.g. as a comparison baseline); the query/retention methods `queryDataPoints`, `queryAggregates`, `applyRetention`, `storageStats`; the waveform-sweep pair `waveformPathsBeforeRecentRuns` / `forgetWaveformPaths`; and the `dataChanged` broadcast stream. Two bulk/enumeration hooks keep the hot paths off an N+1 fan-out against the single-writer SQLite worker: `recentTrendsFor` (bulk `recentTrend`, priming the Pro flaky-retry cache for a whole run in one query) and `distinctTestIds` (the recent-tests enumeration surface). `markRunFinished(runId, finishedAt)` stamps a run's finish time so crash reconciliation does not false-positive a normally-completed GUI run (whose row is created lazily by `recordTrendPoint` with a null `finished_at`); the default is a no-op. Implementations inherit the defaults via `extends TrendStore` (not `implements`). The default `dataChanged` stream is never-emitting; SQL-backed implementations override it with a `StreamController<void>.broadcast()` they fire after every mutation. The default `queryAggregates` returns an empty list (so naïve mocks satisfy the interface for free) and concrete stores override with native time-bucketed aggregation.
- **`SqlTrendStore` (extended)** — `lib/services/trend_store/sql_trend_store_io.dart`. Implements every new `TrendStore` method with native SQL queries against the indexed `test_results` table. `queryDataPoints` is one parameterized SELECT. `queryAggregates` pulls the matching rows, then groups in Dart using a fixed origin and bucket size (the percentile computation reuses the canonical `computeRuntimePercentiles` helper). `applyRetention` runs an age-based DELETE followed by, optionally, a row-count-based DELETE — either oldest-first (single `DELETE … ORDER BY started_at ASC LIMIT N`) or lowest-value-first (keeps the newest `0.75 × maxDataPoints` rows densely and thins the older slice at a fixed cadence so the total lands on `maxDataPoints`) — then, when anything was deleted, prunes orphaned `runs` rows and VACUUMs only when enough dead space has accumulated. `storageStats` is two COUNTs plus one MIN/MAX query. The store fires `_notifyChanged()` after every successful mutation (record, batch ingestion, run summary, retention prune) so UI consumers refresh. It also owns crash reconciliation: `markRunFinished` runs a single scoped `UPDATE runs SET finished_at = ? WHERE id = ? AND finished_at IS NULL` at run completion, and `reconcileInterruptedRuns` (invoked at open) marks every run still carrying a null `finished_at` as `interrupted` in its metadata — so only runs whose process died before finalizing are flagged, readable via `isRunInterrupted`. Waveform-dump retention on disk is a separate axis from row retention: `DumpRetentionPolicy` (`lib/services/job_scheduler/dump_retention.dart`) caps the retained per-test working directories across **every** run under `<runRoot>/runs/` — newest-first by mtime under a keep-last-N-failures count and a total-byte ceiling — pruned off the UI isolate at run completion; an empty `.simcrux-keep` marker file pins a directory (or, at the run level, a whole run) against pruning, and in-flight runs are excluded from ranking so a live run's work dir is never deleted under the running simulator.
- **`retentionPolicyProvider`** — `lib/features/settings/providers/retention_policy_provider.dart`. `NotifierProvider<RetentionPolicyNotifier, RetentionPolicy>` exposing the active retention policy, persisted in `AppSettings` (default `RetentionPolicy.defaultPolicy`: 30 days, 50 000 data points, oldest-first, waveforms from the last 10 runs). The open-core `RegressionRunner` reads this provider and, best-effort after every completed run, calls `trendStore.applyRetention(policy)` and sweeps older waveforms, so trends.db and the waveform archive stay bounded in every tier without user action. The Pro overlay overrides the notifier so an organization policy can lock it, and its Settings → Retention category edits it. Tests override it to install custom policies.
- **`perTestTrendChartOpenerProvider` / `perSuiteTrendChartOpenerProvider`** — `lib/features/trend_tracking/providers/trend_screen_openers.dart`. `Provider<TrendScreenOpener?>` typed as `void Function(BuildContext context, {String? testId, String? suiteId})`. Open-core default is `null`: the menu and command-palette entries stay visible (users discover the capability) and firing one shows the "requires SimCrux Pro" snackbar. The Pro overlay's opener checks `proFeatureUnlocked` and opens the per-test / per-suite trend chart (or the upgrade dialog), and the overlay adds its own dashboard-row trend entry. The optional `testId` / `suiteId` hints pre-populate the picker when the caller has a specific target.
- **`calendarHeatmapOpenerProvider` / `retentionPolicySettingsOpenerProvider`** — same shape as the chart openers but using the simpler `TrendScreenOpenerSimple = void Function(BuildContext)` typedef. The heatmap and retention settings open the same screen regardless of caller context.
- **`SimcruxAction.showTrendChart` / `showSuiteTrendChart` / `showCalendarHeatmap` / `configureRetentionPolicy`** — Pro-tier action enum values, defined in open core for the command palette / menu inventory. Each dispatches through its matching opener provider in the action-handler map (`lib/core/shortcuts/simcrux_action_handlers.dart`). All four are on the documented `noDefaultBindings` list — they are drill-down workflows reached from another surface (a selected test, a dashboard row, the command palette), so they do not earn a headline keyboard chord.

### Custom simulator-driver plugin SDK extension surfaces (open-core)

The plugin SDK lets users extend SimCrux with custom simulator drivers — vendor wrappers (xsim, Questa, VCS, Xcelium) or community implementations for less-common simulators (CXXRTL, surelog-based flows). Open-core ships the SDK contract (manifest, wire protocol, registry interface) and threads the registry through the runner; the subprocess-based loader implementation lives in the Pro overlay because spawning external code is a Pro-tier feature. The full contract lives in [`include/simcrux_driver_plugin_abi.md`](../include/simcrux_driver_plugin_abi.md).

**Process isolation is non-negotiable.** Drivers run as separate OS subprocesses, not in-process via `dart:ffi`. This keeps host licensing posture independent of plugin licensing (GPL'd or proprietary vendor wrappers stay confined to their own process) and ensures a buggy plugin cannot bring SimCrux down. Implementations that try to embed drivers in-process violate the open-core/Pro contract.

- **`SimulatorDriverPluginManifest`** (`lib/domain/models/simulator_driver_plugin_manifest.dart`) — immutable manifest model. Reads YAML (the on-disk authoring format, `fromYaml`) or a decoded map (`fromMap`), and writes JSON via `toJsonString` for cross-tool pipelines. Fields cover identity (`pluginId`, `displayName`, `description`, `version`, optional author / homepage / repository), licensing (`licenseSpdx`), runtime contract (`executablePath`, `stdioProtocol`, `abiVersion`, `minSimcruxVersion`), capability surface (`supportedSimulators`, `declaredCapabilities`). Forward-compatible — unknown top-level keys and unknown capability values are silently ignored so newer plugins keep loading on older hosts. The host enforces `abiVersion == kSimcruxDriverPluginAbiVersion` and rejects mismatches with a logged diagnostic. The `kSimcruxDriverPluginAbiVersion` constant is the single source of truth; major bumps follow the deprecation policy in `include/simcrux_driver_plugin_abi.md`.
- **`DriverCapability`** (`lib/domain/enums/driver_capability.dart`) — vocabulary of features a plugin can advertise: `compile`, `run`, `coverage`, `waveformDump`, `interactiveDebug`, `parameterSweeps`, `liveProgress`. Today the set is mostly informational: the only capability that changes host behavior is `compile` (it decides whether the plugin driver reports a separate compile step), and the Pro Settings → Plugins section lists each installed plugin's declared capabilities. No host surface is gated on the others yet. Forward-compatible: unknown wire ids are silently skipped during manifest decode.
- **`DriverStdioProtocol`** (`lib/domain/enums/driver_stdio_protocol.dart`) — wire-format enum. v1 ships only `jsonLines` (line-delimited JSON over stdin/stdout, `\n` terminated); the enum exists so future revisions can add formats without a breaking change.
- **`DriverWireMessageKind`** + **`DriverWireCodec`** + **`DriverRequest`** / **`DriverResponse`** (`lib/services/driver_plugin/driver_wire_protocol.dart`) — the JSONL envelope schema. Six request kinds (`initialize`, `compile`, `run`, `cancel`, `shutdown`, `queryCapability` — reserved, not sent by ABI 1 hosts) and eight response kinds (`initialized`, `compileProgress`, `compileComplete`, `runProgress`, `runComplete`, `log`, `error`, `capabilityQueried`). The `spec` object of `compile` / `run` is built by `encodePluginTestSpec` (`lib/services/driver_plugin/plugin_test_spec_codec.dart`). Every envelope carries a monotonically increasing `requestId` so multi-request correlation works. `DriverRequests` / `DriverResponses` factory constructors keep payload-shape knowledge centralized. Decoding raises a typed `DriverProtocolError` so call sites distinguish wire-contract violations from driver-side error envelopes; the codec raises `malformedJson`, `missingField` and `unknownKind`, while `DriverProtocolErrorKind.handshakeTimeout` / `abiMismatch` are defined but not currently raised (the Pro loader reports handshake failures as instantiation errors).
- **`SimulatorDriverPluginInterface`** (`lib/domain/interfaces/simulator_driver_plugin_registry.dart`) — extends `SimulatorDriver` so plugin-backed drivers consume through the same runner surface as built-ins, and adds `manifest` (introspection) + `shutdown()` (graceful teardown). The Pro overlay's subprocess registry returns instances of this interface from `instantiate`.
- **`SimulatorDriverPluginRegistry`** (`lib/domain/interfaces/simulator_driver_plugin_registry.dart`) — abstract registry interface. Three concerns: `listInstalled` enumerates manifests in the configured plugin directory; `instantiate(pluginId)` spawns the subprocess + performs the initialization handshake; `events` exposes a `Stream<PluginEvent>` for lifecycle events (`PluginInstalled`, `PluginRemoved`, `PluginCrashed`, and `PluginUnresponsive`, which is defined but not currently emitted — a hung plugin is killed by the run heartbeat and reported as `PluginCrashed`). `shutdownAll()` gracefully terminates every active subprocess on app exit. Open-core ships `NoopSimulatorDriverPluginRegistry` (lists nothing, instantiates nothing, emits no events) as the default; the Pro overlay registers a registry that behaves like the no-op until the user grants the plugin-safety acknowledgment, then delegates to its subprocess loader.
- **`simulatorDriverPluginRegistryProvider`** (`lib/services/driver_plugin/simulator_driver_plugin_registry_provider.dart`) — Riverpod seam. Default `NoopSimulatorDriverPluginRegistry`; Pro overlay overrides via `proOverrides`. Threaded into `simulatorDriverRegistryProvider` so `LocalJobScheduler` resolves plugin-contributed drivers via the registry's `resolveDriverFor` async hook.
- **`installedPluginsProvider`** (same file) — `FutureProvider<List<SimulatorDriverPluginManifest>>` consumed by the Pro Settings → Plugins section's installed list. Invalidated to re-fetch after a reload (the `reloadPlugins` action / the section's Reload button) and after the Pro install-from-zip, uninstall and per-plugin disable flows.
- **`pluginEventsLogProvider`** (same file) — `StreamProvider<List<PluginEvent>>` that buffers the last `kPluginEventsLogCapacity` (= 100) events from the active registry. Rendered by the Pro Settings → Plugins section's recent-events list; bounded so memory stays predictable under flaky plugins that crash repeatedly.
- **`SimulatorDriverRegistry.resolveDriverFor(simulatorId)`** (`lib/services/simulator/simulator_driver_registry.dart`) — async lookup that consults built-ins first, then the optional plugin registry. **Precedence rule:** built-in drivers win on name collision. If a plugin claims the same simulator id as a built-in driver (e.g. a plugin claiming `verilator`), the plugin is silently shadowed and the built-in is used. This guarantees that installing a plugin never accidentally changes the behavior of a built-in simulator. Plugin authors who want to override a built-in must publish under a different simulatorId (e.g. `verilator-experimental`) and have users explicitly opt in via their `TestSpec`. `LocalJobScheduler` calls this method instead of the sync `driverFor`. The sync `driverFor` is retained for the cases that genuinely only need built-ins (Settings → Simulators inventory, diagnostics).
- **`SimcruxAction.openPluginManager` / `reloadPlugins`** — action enum values defined in open core with `requiredTier: LicenseTier.pro`, for the command palette / menu inventory. Both categorized under `ActionCategory.tools` and dispatched through the nullable opener seams in `lib/services/driver_plugin/plugin_action_openers.dart` (`pluginManagerOpenerProvider` / `reloadPluginsOpenerProvider`). Open-core builds register both actions so they stay discoverable, but the opener defaults are null so dispatch surfaces the Pro-gated snackbar. The Pro overlay's openers open a Plugin Manager dialog hosting the Plugins section and re-scan the plugin directory (invalidating `installedPluginsProvider`, reporting the installed count — or pointing at Settings → Plugins while the safety acknowledgment is ungranted).

## 12. Glossary

| Term | Definition |
|------|------------|
| **CXP** | Cross-Tool eXchange Protocol — the peer cross-probe protocol shared across the four Crux products (WaveCrux, NetCrux, LintCrux, SimCrux) and any third-party tool that implements the v1 spec. Defined in the `crux_cxp` package under `crux-shared` and specified at `https://edacrux.app/cxp`. SimCrux is one of the four reference implementations. |
| **CxpServer** | The abstract `CxpServer` interface in `crux_cxp`, with concrete `LocalCxpServer` (TCP/JSON-line on localhost) and `NoopCxpServer` implementations. SimCrux wraps `LocalCxpServer` in `SimCruxCxpServer`. |
| **CxpClient** | Symmetric counterpart to `CxpServer`. SimCrux dials every discovered peer through `crux_cxp`'s `CxpPeerConnector`, which opens a `LocalCxpClient` per peer; tests and external tools use the same client to drive a SimCrux instance. |
| **ElementId / ElementKind** | Cross-product element identifier carried on the CXP wire. Ten kinds covering signals, scopes, instances, nets, ports, markers, rules, tests, breakpoints, and source-code locations. |
| **NameResolver** | The seam each Crux product implements (here `SimCruxNameResolver`) to translate its native references into and out of canonical `ElementId` form. |
| **NotifySelection** | v1 CXP broadcast message — peer announces its current selection. SimCrux emits these when the selected test or source file changes, while the CXP server is running and "broadcast selection" (`broadcastSelectionOnCrossProbe`) is on. |
| **RequestHighlight / RequestHighlightAck** | v1 CXP imperative — peer asks another to focus on a specific element. | **RequestOpenSource / RequestOpenSourceAck** | v1 CXP imperative — peer asks another to open a source-code location in the configured editor. SimCrux's handler shells through `EditorLauncher`. |
| **SimCruxCxpServer** | Open-core wrapper around `LocalCxpServer` that registers `SimCruxNameResolver`, the default port `54325`, and the `simcrux.debug` capability advertised in the handshake. Lives at `lib/services/remote/cxp/simcrux_cxp_server.dart`. |
| **SimCruxNameResolver** | The opaque-passthrough resolver SimCrux uses. Documents the v1-vocabulary constraint that waveform files ride `ElementKind.source` in `RequestHighlight`; CXP 1.1's `request_open_artifact` (with `waveform` / `source` artifact kinds) is the dedicated open message, and SimCrux's inbound handler answers it. |

| **`simcrux.suggested_signals`** | Metadata key SimCrux uses on outbound `NotifySelection` messages to suggest signals to a WaveCrux receiver before the imperative `RequestHighlight` fires. Forward-compatible — receivers that don't recognise the key ignore it. |
| **`riscvStreamCoordinateFor`** | The RISC-V trace-coordinate producer, at `lib/services/remote/cxp/riscv_stream_coordinate.dart`. Derives the optional CXP §9.9 `coordinate` payload field from a `TestResult`, so the hand-off names *where in the trace* rather than only *which trace*. Pure and ungated. **Returns null for almost every row, on purpose:** §9.9 forbids emitting an index the producer cannot state in the named stream's own index space.
